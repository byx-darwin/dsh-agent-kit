## 接口

```ts
const r = await ctx.dingtalk.send({
  text: '纯文本',                       // 或 markdown: '## 标题\n正文'
  target: { chatId: 'cid...' },        // 或 { userId } / { openDingtalkId }
  at: { openDingtalkIds: ['...'] },   // 也支持 all: true
  idempotencyKey: 'evt_...',
  traceId: 'evt_...',
  signal,
})
// r.results: Array<{ target, ok, messageId?, error? }>
```

仅支持当前 `dws` 登录的 `user` 身份，不提供机器人或 webhook 身份。`target` 省略时使用配置的 `defaultTarget`；目标、@ 列表和幂等键会先经过格式校验。给出 `idempotencyKey` 时，可重试的失败最多重试 `retry.maxAttempts` 次；否则不自动重试，避免重复发送。

## 查找业务插件的转发目标

业务插件可以用 `ctx.dingtalk.searchRecipients('group', '群名关键词')` 或 `searchRecipients('user', '姓名')` 查询当前登录账号可见的候选。返回项带真实 `{ chatId }`、`{ userId }` 或 `{ openDingtalkId }` 和 `complete` 标记；重名时由配置人员明确选择，不自动采用第一项。业务插件也可在自己的设置字段上声明 `kind: 'dingtalk-target'`，让本机设置页提供群/个人搜索与选择。此操作只保存业务插件自己的发送目标，不影响下方“群消息进入哪个插件”的路由；查找不会发送消息。

<h3 id="login">登录状态与登录</h3>

```ts
const status = await ctx.dingtalk.status()
const session = await ctx.dingtalk.login()
await showToUser(session.verificationUrl)
const after = await session.completed
await ctx.dingtalk.logout()
```

`login()` 启动 `dws auth login --device --no-browser` 并返回真实授权链接；扫码授权完成后 `completed` 返回最新状态。`logout()` 只退出当前账号，不退出同机的其他 dws 账号。启动时以及每隔 `preflightIntervalMs` 检查登录状态；`dryRun: true` 时不真实发送，也跳过启动登录检查。

<Notice title="dws 登录是本机共享的" tone="warn">
登录态属于运行 Profile 的系统用户，同一用户下使用 dws 的其他程序也会看到登录与退出的结果。组织必须授予 CLI 数据访问权限，扫码登录本身不能绕过权限限制。
</Notice>

`dwsPath` 必须是可执行文件的绝对路径；省略时从 `PATH` 查找。Windows 上可以自动解析 npm 的 `dws.cmd` 到实际的 `dws.js`，手动指定时请直接指向 `.exe` 或 `.js`。

## 群内 @ 消息路由

在 Agent Kit 设置页的钉钉卡片中，可添加“群 ID → 业务插件 ID”映射，并从未命中消息选群。群名仅用于展示。插件用相同 ID 注册接收器：

```ts
export const inject = ['dingtalk']
export async function apply(ctx: Context) {
  const sub = ctx.dingtalk.onPluginMessage('business-orders', async (message, { signal }) => {
    await handleOrder(message.content, { eventId: message.eventId, signal })
  })
  await sub.ready
}
```

对应配置为 `groupRoutes: [{ conversationId: 'cid-orders', pluginId: 'business-orders' }]`。一个群只会转给一个目标插件；目标插件未注册时记入未命中，不回退给其他插件。设置页的业务插件列表提供 ID 输入建议，但登记设置项不等于注册了消息接收器。

兼容旧接口：业务插件仍可用 `ctx.dingtalk.onMessage({ conversationId, match?, priority? }, handler)` 在代码中注册规则，设置页配置的群优先走指定业务插件。旧接口先按群的 `conversationId` 匹配，再由可选的 `match` 判断正文；数值更高的 `priority` 优先。每条消息只交给第一个命中的处理器，不会广播给所有插件。

```ts
export const inject = ['dingtalk']

export async function apply(ctx: Context) {
  const sub = ctx.dingtalk.onMessage(
    { conversationId: 'cid-orders', match: (m) => m.content.startsWith('工单') },
    async (message, { signal }) => {
      await handleOrder(message.content, { eventId: message.eventId, signal })
    },
  )
  await sub.ready
}
```

Agent Kit 为全部业务插件共用一个常驻的 dws `@我` 事件监听进程。插件卸载时自动注销规则，但监听继续记录未命中的消息，Service 卸载时退出。最近 200 条未命中记录会保留群 ID、可查到的群名、时间和最多 240 字预览；可在本机设置页的钉钉卡片查看，或调用 `ctx.dingtalk.unmatchedMessages()` 读取。dsh Profile 下按 dws 账号分别保存于 `.agent-kit/dingtalk-unmatched/<账号哈希>.json`，不会自动转发给其他插件。`message.content` 是不可信输入；业务插件负责校验、决定是否回复。进程内按 `eventId` 去重，但重启后仍可能重复投递，业务处理需自行幂等。`dryRun` 模式不能启动监听。
